How it compares

Remoc is stateful. A call can hand the other side a channel or an object that stays alive after the call returns, which puts it in the family of DCOM and CORBA rather than of the request-and-response RPC that grew up on HTTP.

Nothing to generate

There is no schema file, no compiler to install and no build step to arrange. The types you send are the ones you already have, with #[derive(Serialize, Deserialize)] on them. The channels are the ones you already use — mpsc, oneshot, watch, broadcast — with the methods they have in tokio::sync. A trait becomes remotely callable by putting #[rtc::remote] on it.

When both ends are Rust, a schema would only put a second type system in front of your own: an enum with data becomes a union and a wrapper message, a Result becomes a status code and a detail to parse back. That is a translation you would write in both directions, on both sides, and keep in step with your types by hand.

The step from a local program to a distributed one is correspondingly small: keep the types, keep the channels, hand one end of a connection to the other side. What you have to learn is how the connection is set up, not an interface language — and when a type changes, the compiler tells both sides.

Stateful, not request and response

In request-and-response RPC every call stands alone: a method, arguments, a result. Anything that keeps going needs a stream declared in the schema, or a second connection, or an identifier you invent and look up on both sides.

A Remoc call can hand over a thing instead. Put an rch::mpsc::Sender in the request and the peer holds a live channel it can push into for the next hour; return an rch::watch::Receiver and the caller sees every change from then on; hand out an rtc client and the peer calls your object. None of it is registered anywhere and none of it needs a port: the channel exists because you sent one, inside the connection that was already open.

Two conversations over the one connection, with nothing to correlate: the stream is the value the call returns or takes. Elsewhere each would be a streaming method in a schema, or an identifier you mint and look up on both sides.

Latency is not the price for it. Channels do not wait for acknowledgement, so values keep flowing without a round trip between them, and independent calls need not be made one after another: join!(c.a(), c.b(), c.c()) puts three requests on the wire together and gets three results for one round trip. That holds however the rtc server was started — with serve(false) the requests queue and run one after the other, with serve(true) they run at once, a task each, because underneath it is an mpsc channel like any other.

The model is older than the web, and the systems built on it — CORBA, DCOM, .NET Remoting — are mostly remembered for failing. What sank them is worth naming: calls made to look local so that failure arrived unannounced, object lifetime kept by distributed reference counts, leases and liveness pings, dynamic ports no firewall would pass, and specifications no two vendors implemented alike. Remoc keeps the model and drops all four. Every call hands you a Result, lifetime is a channel closing, everything rides the one connection you already have, and there is no interface language, no object request broker and no naming service.

What that gets you

Back pressure everywhere

Every channel, remote function and trait call rides a port with credit of its own, so a receiver that stops reading stalls its own sender instead of filling the peer's memory. Nothing to arrange per call site.

Errors stay typed

A call returns your own error enum, not a status code with a detail to parse or a string to match on. What can go wrong in the transport arrives as CallError, which converts into your type.

Either end can serve

Who opened the connection has nothing to do with who offers the service. A device that dials out through NAT can hand its peer a client and be called back over the same connection.

Channels are cheap to open

A new one is usable at once: the port is pre-connected, so the first message leaves without waiting for the other side to accept it. Open one per request if that is the natural shape.

The browser can be one end

Remoc compiles to wasm32 and runs over a WebSocket, so a tab talks to your server in Rust: the same types, the same traits, no second implementation of the protocol in TypeScript. Only what the view needs crosses into JavaScript.

One connection, whatever it is

Every channel, call and object shares the single link you already have — one port to open, one hole in a firewall. That link can be TCP, TLS, a WebSocket, a pipe or anything else that carries bytes, and nothing above it changes.

The alternatives

gRPC, through tonic

The most widely deployed of them. A .proto schema defines the methods, tonic generates the Rust from it, and anything that speaks gRPC can call you: Go, Python, a browser through a gRPC-Web proxy.

gRPC is defined over HTTP/2, so the transport is settled for you — which is the point if your routing, authentication and metrics already live in that layer, and a constraint if they do not. The roles come with it: the side that dials consumes the service and cannot offer one back over the same connection.

It is stateless by design, and that is what makes it scale across replicas behind a load balancer. Streaming exists, but each stream is a method in the schema and nothing outlives the call it belongs to; anything that has to persist between calls lives in a store, keyed by an identifier the client carries along.

tarpc

The closest neighbour: tarpc puts Rust on both ends, asks for no schema and turns a trait into a client and a server, which is what rtc does as well. For plain request and response the two are interchangeable, and tarpc deliberately stops there: a call takes values and returns values, and between calls the server holds nothing for you.

Cap'n Proto

Cap'n Proto is the exception among the three, and the other system built on references you can pass around: a message may carry a capability, and whoever receives it can call it. It works across languages, at the price of a schema language and its compiler.

Its promise pipelining has no Remoc equivalent — calling a method on a result that has not arrived yet, so a chain of calls costs one round trip. Remoc usually inverts that problem instead: you send a channel into the call, so the path for the answer exists before the call is made. What remains missing is chaining calls onto a result whose type is only known once the previous one returns.

Where the contract lives

There is no schema file, but there is a contract: the traits carrying #[rtc::remote] and the types they pass. Put them in their own crate, publish it, and both ends depend on a version of it — the same versioning you already use for everything else in Cargo.

Endpoints on different versions still talk. The default Postbag format is self-describing, so a field added with #[serde(default)] is filled in when an older peer omits it, and a field it does not know about is ignored rather than fatal. That covers most of what changes over the life of a program.

When the data itself has to be reshaped rather than extended — a field split in two, two merged, a type replaced — the versioned module holds the old and the current representation side by side and converts between them, per value and per peer.

When Remoc is not the right choice

A peer is not Rust

The contract is Rust types, so both ends are built from them. When one end cannot be, that is what gRPC and Cap'n Proto are for.

Policy per call in the network

A connection tunnels through HTTP infrastructure happily, as TLS or a WebSocket. But to a proxy in between it is one stream, not a sequence of calls, so per-method routing, rate limiting and metrics have to live in your code rather than in the mesh.
