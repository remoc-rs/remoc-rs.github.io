Bidirectional Rust RPC over one connection

Classical RPC is request and response: the client asks and the server answers. But often the server has something to say on its own, for example a finished job, a changed value or an incoming event. Remoc lets an RPC return a channel for server push or accept a client callback. Requests, streamed updates and reverse-direction calls share the same connection; the server does not need a second connection back to the client.

The limits of request and response

In a request/response framework the server cannot start a conversation. Polling wastes requests and adds latency.

Compared with gRPC: Server-streaming methods cover subscriptions, but each stream is tied to the method that opened it and cannot be passed around. The server still cannot invoke anything on the client.

A second connection in the reverse direction requires the client to be reachable, which fails as soon as it sits behind NAT or a firewall.

Callbacks and transferred channel endpoints

In Remoc, channel endpoints are values that calls can return and accept. A method returns an rch::mpsc::Receiver and the client has a subscription; it returns an rch::watch::Receiver and the client always sees the latest value; the client puts a sender into a request and the server reports progress into it. Each channel keeps working after the call that created it has returned.

For callbacks, choose the shape that fits your interface:

  • A remote function wraps a closure with rfn::RFn. Pass it to the server, which calls it with typed arguments.
  • A client-served trait exposes several related methods. Implement a trait carrying #[rtc::remote] on the client and pass its generated client object to the server.

Compared with gRPC: Bidirectional streaming exchanges messages in both directions within a streaming method. Remoc supports that through channels, but a callback is a separate callable value with its own arguments and result. The server invokes it on demand over the existing connection, without the client polling for callback requests.

Return a channel from an RPC method

This trait is from the counter example. The watch method returns a watch channel receiver, giving the client notifications when the value changes. Its count_to_value() method similarly returns an mpsc receiver for a sequence. Use watch for the latest state; use mpsc when the receiver must read each item in a stream.

Server-to-client RPC callbacks: the pizzeria example

The pizzeria example uses the remote-function option. Its shared Progress type is a rfn::RFn<(String,), ()>: it accepts a progress message and returns no value.

  1. The client wraps its progress handler with Progress::new_1 and passes it to order().
  2. After each preparation step, the server calls progress.try_call(...) with a progress message.
  3. The supplied closure runs back in the client process while the order runs on the server.

Both directions use the one TCP connection opened by the client. The example includes all source files and run commands; OpenTelemetry export is optional.
