Tokio-style remote channels between Rust processes

Need an mpsc channel between two Rust processes or machines, rather than between tasks in one process? Remoc provides Tokio-style mpsc, oneshot, watch and broadcast channels over TCP or another transport. You can send a channel endpoint over the network inside a message, then keep using it over the existing connection.

Channels at a process boundary

Programs get split for good reasons. Work moves to another machine, a privileged part is separated from a user interface, or a component becomes a service of its own. The channels that connected the tasks cannot cross the new boundary, and what used to be a single send now requires a socket, a wire format, framing and dispatch code.

Other approaches: Replacing the channels with a hand-rolled protocol changes the shape of the program: the protocol grows a message enum and match statements on both sides, and every new interaction touches all of them. An RPC framework such as gRPC restructures the code into request and response services, which is a different model than the tasks and channels you started with.

Channels over one connection

Remoc provides MPSC, oneshot, watch and broadcast channels with the API you already know from Tokio. Their endpoints are ordinary Serde values, so you can send a channel over the network inside a message, like you would hand its endpoint to another task. Each channel is typed and all channels between two peers are multiplexed over one connection, which may be TCP, TLS, QUIC, a WebSocket, a UNIX socket or a pipe.

The program keeps its architecture. Tasks still talk through channels; some of those channels now happen to cross a process or machine boundary.

Choose the channel for the conversation

  • mpsc: commands or a stream of items for one receiver.
  • oneshot: a single reply or acknowledgement.
  • watch: the latest state, rather than a history of changes.
  • broadcast: events for several subscribers.

From Tokio mpsc to a channel over TCP

The channel type comes from remoc::rch instead of tokio::sync and the message derives Serde. Sending and receiving follow the same pattern, with an additional error result when receiving remotely. These excerpts assume an established connection.

The complete mpsc-over-TCP example includes connection setup and run commands for both processes. The client sends an mpsc sender inside CountReq; the server sends numbers back through it.
