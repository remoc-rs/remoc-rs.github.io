Overcome per-flow bandwidth limits

Sometimes an internet connection has plenty of capacity, yet a single TCP transfer only achieves a small fraction of it. Aggligator distributes one logical connection across multiple independent transport flows so that a single stream can use their combined throughput.

Why one TCP connection can be slow on a fast line

Tools that open many parallel connections, such as iperf3 -P or multi-connection download managers, often achieve much higher speed than a single transfer over the same line. This usually happens for one of two reasons:

  • Per-flow traffic shaping: the provider or a middlebox limits bandwidth per TCP flow (source and destination address and port) rather than only capping the line as a whole.
  • High latency and packet loss: on long-distance paths with a high bandwidth-delay product, loss-based TCP congestion control shrinks its sending window after a dropped packet and takes many round trips to recover.

Opening more application streams inside one connection does not avoid either limit, because all traffic still shares the same outer TCP flow.

Method TCP flows App interface Per-flow limit
Single TCP connection 1 1 stream ✗ limited to one flow
Multiplexed streams (HTTP/2, yamux) 1 many streams ✗ limited to one flow
Parallel transfers (iperf3 -P) many many connections ± needs app support
Aggligator many 1 stream ✓ combines flows

Splitting one stream across multiple flows

Aggligator accepts a single byte stream from the application and sends its packets across multiple independent transport links. The receiving endpoint reorders the incoming packets back into one stream and resends unacknowledged data if a link fails.

To get higher throughput in practice, three settings matter:

  • Multiple flows at the bottleneck: open several parallel links with set_links_per_path on the TCP, SOCKS5 or WebSocket connector (or --tcp-links and --socks-links in agg-tunnel).
  • Buffer sizes: on high-latency paths with many links, increasing send_buffer and recv_buffer in the configuration allows enough in-flight data to keep all links busy.
  • Congestion control: enabling BBR (--tcp-congestion bbr) prevents occasional packet loss from throttling individual TCP links.

In a practical user report on a line where each outgoing TCP flow was throttled to 2.5 Mbit/s, combining 16 parallel flows with Aggligator raised the throughput of a single logical connection to about 180 Mbit/s.

Direct TCP: multiple parallel links per path

When connecting directly over TCP, calling set_links_per_path on TcpConnector (or passing --tcp-links to agg-tunnel) opens multiple TCP connections with distinct source ports over each network path.

SOCKS5 proxies: multiple tunnel or proxy paths

When traffic goes through local tunnel instances (such as ssh -D or an encrypted proxy client) or remote SOCKS5 servers, the SOCKS5 transport can combine several proxy endpoints, or open multiple parallel links through one proxy with set_links_per_path (--socks-links).
