Rust IPC over Unix sockets, named pipes and child-process pipes

Many programs are really several processes that need to talk, for example a daemon and its command-line client, a privileged helper and a user interface, or a plugin running as a subprocess. Remoc provides async Rust RPC and typed channels over Unix domain sockets, Windows named pipes or a child process's stdin and stdout, without a separate protocol schema.

Defining an IPC interface

The operating system gives you a byte stream for inter-process communication, but what the processes actually need are commands with typed arguments and results, progress and event notifications, and an interface that can grow without breaking installed clients.

Other IPC approaches: A hand-rolled protocol over a UNIX socket means framing, a message enum and dispatch code that grow with every command. JSON over stdin and stdout is quick to start with, but untyped and without a versioning story. D-Bus integrates well with system services, but brings a bus daemon and its own type system. gRPC over a UNIX socket uses a separate .proto schema and generated message and service code.

Your Rust traits as the interface

With Remoc, the daemon's interface is a Rust trait carrying #[rtc::remote], which generates the client and server implementations. Arguments and results are ordinary Serde types. A method can return a channel for later events, or accept a channel endpoint inside a request. The channels work in both directions over the same connection.

Since Remoc serializes with the Postbag codec, the interface can evolve. You can add fields, methods and enum variants and an updated daemon keeps understanding an older installed client, without version negotiation code.

The transport is whatever local byte stream suits you: a UNIX socket, the stdin and stdout pipes of a child process, a named pipe on Windows or a TCP connection on localhost. Remoc implements no transport itself, so nothing else is pulled in.

A local daemon and its clients

The timer daemon example is a complete daemon and CLI, using Unix sockets on Unix and named pipes on Windows. Timers belong to the daemon: a client can add a reminder and exit while the timer keeps running.

  • timerctl add 30s "Check tea" schedules a reminder and exits.
  • timerctl list lists pending reminders.
  • timerctl watch receives future completions on a broadcast receiver returned by an RPC call.
  • timerctl add 30s "Check tea" --wait sends a oneshot sender inside the request and waits for that timer's completion.

The add call returns an identifier, not the eventual completion. To wait, the client creates a oneshot channel, keeps its receiver and includes the sender in the serializable NewTimer struct:

consume() establishes Remoc and receives the RPC client handle sent by the daemon's provide(). Both helpers start the connection I/O in a background task. The daemon separately runs server.serve() to dispatch calls to its service implementation.

The oneshot reply and RPC traffic share the same connection. Watchers use their own connections and receive the same completion through broadcast channels. Disconnecting a waiting client does not cancel the timer or stop other watchers.

Choosing the local transport

The example's local::connect and listener hide only the operating-system-specific setup:

  • Unix: UnixListener and UnixStream use a filesystem socket path, such as the example's default timerd.sock.
  • Windows: Tokio's named-pipe server and client use a name such as \\.\pipe\remoc-timerd. The listener creates another pipe instance for each new client.

Each accepted stream is split and passed to Connect::io. The shared trait, timer implementation and client calls are unchanged between platforms. To adapt a TCP-based service, replace its listener and connect code in the same way.

Child-process IPC over stdin and stdout

For a worker or plugin that the parent starts itself, RPC can use pipes instead of a listening socket:

  1. Spawn the child with tokio::process::Command and piped stdin and stdout.
  2. In the parent, pass the child's stdout as the reader and its stdin as the writer to Connect::io.
  3. In the child, pass its own stdin as the reader and stdout as the writer to Connect::io.

The existing child-process transport example shows both sides. It uses placeholder request and response types to illustrate the transport setup; substitute your application's types. Further channels, callbacks and remote trait clients travel over that same connection.

Keep stdout reserved for Remoc's protocol and send logs to stderr. Retain the child handle if the parent needs to wait for its exit or restart it.
