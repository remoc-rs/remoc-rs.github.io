Example: a timer daemon and CLI

A Rust daemon schedules reminders independently of the clients that add them. The same RPC interface works over Unix domain sockets on Unix and local named pipes on Windows. Clients can list pending timers, wait for one completion or watch all future completions.

{% include example-tabs.html %}

RPC methods

  • add(NewTimer) schedules a reminder and returns its identifier without waiting for it to finish.
  • list() returns the reminders that have not finished yet.
  • subscribe() returns a broadcast receiver for future completions.

Each client has its own Remoc connection, but the daemon serves the same timer state to all of them. A timer belongs to the daemon, not to the connection that scheduled it.

This is a foreground example with in-memory state, not an installed system service. Stopping the daemon discards its timers. For a smaller introduction to RPC, start with the counter example.

Running the daemon and CLI

Clone the repository:

git clone {{ site.repo }}
cd remoc

In the first terminal, start the daemon:

cargo run --manifest-path examples/daemon/Cargo.toml --bin timerd

In a second terminal, watch completions:

cargo run --manifest-path examples/daemon/Cargo.toml --bin timerctl -- watch

In a third terminal, add a reminder and list pending timers:

cargo run --manifest-path examples/daemon/Cargo.toml --bin timerctl -- add 30s "Check tea"
cargo run --manifest-path examples/daemon/Cargo.toml --bin timerctl -- list

The add command prints an identifier and exits. When the timer finishes, the watcher prints, for example: 

Finished 1: Check tea

Open another watcher to receive the same notifications in two clients. Completed timers disappear from list.

To wait for one specific timer, use --wait:

cargo run --manifest-path examples/daemon/Cargo.toml --bin timerctl -- add 5s "Check tea" --wait

This client stays connected until its timer finishes. Watchers still receive that completion. Disconnecting the waiting client does not cancel the timer. Use Ctrl+C to stop the daemon, a watcher or a waiting client.

Passing a channel inside a request

NewTimer is a Serde struct containing a duration, a message and an optional rch::oneshot::Sender<Timer>. The channel endpoint travels with the other fields; it needs no separate socket.

  1. With --wait, the CLI creates a oneshot channel. It keeps the receiver and passes the sender in the add request.
  2. The RPC returns the timer's identifier. The daemon keeps the sender until the timer finishes, then sends the completed Timer.
  3. The CLI awaits its receiver over the same connection that carried the RPC call.

watch demonstrates the opposite direction: subscribe() returns a channel receiver from the daemon. The daemon keeps the broadcast sender and can notify several clients. Each watcher receives future events only, not a history.

See remote channels for the channel types and server push and callbacks for other notification patterns.

Unix sockets and Windows named pipes

Only src/unix.rs and src/windows.rs differ between platforms. Both expose a local listener and a connect function; the RPC implementation and Remoc connection setup stay the same.

  • Unix: the default endpoint is timerd.sock, relative to the working directory. Run all programs from the same directory. The socket permits access only by its owner.
  • Windows: the default endpoint is \\.\pipe\remoc-timerd. The daemon creates another listening pipe instance for each new client.

Both programs accept --endpoint before the CLI command to select another socket path or pipe name. An existing endpoint is not taken over by a second daemon.

Normal Unix shutdown removes the socket file. After a forced termination, first ensure the old daemon has stopped, then remove its leftover socket. For real applications, place it in an application-owned directory.

The IPC guide also covers connecting to a child process through stdin and stdout.

Source code

One package contains the shared interface, the timerd and timerctl binaries, and the two platform-specific adapters. provide sends each client its RPC handle; consume receives it. Both helpers start the background connection I/O, while server.serve() dispatches the method calls.
