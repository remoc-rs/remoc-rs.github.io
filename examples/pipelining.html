Example: pipelining dependent RPC calls

A directory returns a counter's RPC client. Normally, a caller waits for that client before using it. Pipelining lets it queue the counter calls together with the request that opens the counter.

{% include example-tabs.html %}

Sequential and pipelined calls

The example performs the same three operations in both cases:

  1. Open a counter through the directory.
  2. Increase the counter by 20.
  3. Read its value.

The sequential version awaits each response before making the next call. The pipelined version creates a placeholder counter client locally and queues the dependent calls with rtc::calls!. The server connects them to the counter when it is created.

The directory's open_counter method is marked #[pipelinable]. This adds a pipelined calling variant without changing how ordinary callers use the method.

Running the comparison

git clone {{ site.repo }}
cd remoc
cargo run --manifest-path examples/pipelining/Cargo.toml

Both endpoints run in one process. The transport forwards frames through in-memory channels with 150 ms of delay in each direction, giving a simulated 300 ms round trip.

  • Sequential: three round trips, about 900 ms.
  • Pipelined: one round trip, about 300 ms.

Both return 20. The program prints the measured times; these illustrate the effect of network latency, not a throughput benchmark.

See the pipelining documentation for the generated calling variants and their use. For a first introduction to remote trait calls, see the counter example.

Source code

A single binary defines the two remote traits, serves their implementations, simulates the delayed connection and runs both calling styles.
